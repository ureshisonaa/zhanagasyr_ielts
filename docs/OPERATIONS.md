# Установка и эксплуатация

## Локальная разработка

Следуйте README. `bash scripts/start-dev.sh` запускает веб-сервер и отдельный обработчик сроков. Ctrl+C останавливает оба процесса. Состояние — в `var/db.sqlite3`, файлы — в `var/private/`; процессы не сохраняются в снимке облачной среды и должны запускаться заново. Используйте существующий checkout: дополнительный Git worktree для облачной задачи не требуется.

Для браузерного smoke-теста нужны `npm ci` и Chromium. По умолчанию путь `/usr/bin/chromium`, другой задаётся `CHROMIUM_PATH`. Выполните `npm run test:browser` при работающем приложении и демоданных. Тест проходит настоящий UI, использует имитированный микрофон Chromium, создаёт ещё одну демонстрационную попытку и публикует результат. Он запрещает запуск на внешнем hostname. Скриншоты сохраняются в игнорируемую папку `var/screenshots/`. За пределами облачной среды можно установить браузер через `npx playwright install chromium` и указать его путь.

## Production

Подготовлены Dockerfile и Compose с PostgreSQL 17, Gunicorn, отдельным timer-процессом и шагом миграций/сборки static. На текущем этапе контейнерное развёртывание на пользовательском сервере **не выполнено**. Перед публичным доступом проверьте конфигурацию на staging.

1. Создайте защищённый `.env` (права 600). Задайте случайные `DJANGO_SECRET_KEY` и URL-safe `POSTGRES_PASSWORD`, домен в `DJANGO_ALLOWED_HOSTS`, `SITE_URL=https://…`, `CSRF_TRUSTED_ORIGINS=https://…`. Не добавляйте секреты в Git. Настройте SMTP при необходимости.
2. `docker compose config --quiet` проверяет конфигурацию без вывода значений секретов.
3. `docker compose up --build -d` запускает БД, выполняет миграции и collectstatic, затем запускает web и timer.
4. `docker compose exec web python manage.py bootstrap_admin --email admin@your-domain.kz` создаёт первого администратора. **Не запускайте seed_demo в production.**
5. Настройте HTTPS reverse proxy к `127.0.0.1:8000`. Compose не публикует PostgreSQL наружу. `TRUST_PROXY=1` допустим только за доверенным proxy, который перезаписывает `X-Forwarded-Proto`; не передавайте клиентское значение этого заголовка напрямую.
6. Прокси должен разрешать запросы до 26 МБ. Static отдаётся WhiteNoise. **Не публикуйте `var/private` или `/media/` напрямую через nginx**: приватные файлы проходят через авторизацию Django.
7. `docker compose exec web python manage.py check --deploy` и `docker compose ps` — обязательные проверки перед запуском. `/health/` проверяет БД, но не заменяет полный сценарий. Настройте мониторинг процесса timer, свободного диска, ошибок HTTP и доставки SMTP.
8. В access logs исключите/замаскируйте токены маршрута `/activate-account/…` и query-параметр `play` у `/media/…`. Прикладной аудит токенов не содержит.

Нельзя обещать согласованную нагрузку на основании локального SQLite-теста. Перед использованием реальными учениками проверьте PostgreSQL, одновременные сохранения, запись Safari/iOS и Android, HTTPS, сеть, права преподавателей, реальные тесты и политику данных.

## Backup / restore SQLite

Остановите web и timer, чтобы согласовать снимок БД с приватными файлами. Создайте резервную копию и восстановите в **новую** папку:

```bash
.venv/bin/python manage.py backup_data var/backups/manual-2026-10-15.tar.gz
.venv/bin/python manage.py restore_backup var/backups/manual-2026-10-15.tar.gz --destination var/restored
SQLITE_PATH="$PWD/var/restored/db.sqlite3" PRIVATE_MEDIA_ROOT="$PWD/var/restored/private" .venv/bin/python manage.py check
```

Архив содержит SQLite online-backup, приватные файлы и SHA-256 manifest. Restore проверяет пути и контрольные суммы, не перезаписывает существующую папку. Сначала выполните проверку целостности БД и наличия файлов, затем настройте `SQLITE_PATH` и `PRIVATE_MEDIA_ROOT` на восстановленные пути либо замените рабочие файлы при остановленных процессах. Секрет Django храните отдельно; для восстановления сессий нужен прежний секрет. При его смене все прежние ссылки/сессии станут недействительными.

Архив содержит персональные данные. Храните его с ограниченными правами и шифрованием на отдельном хранилище. Периодичность, срок хранения и ответственный определяются учебным центром. Встроенного удалённого расписания резервного копирования нет.

## Backup / restore PostgreSQL

Приостановите web/timer и выгрузите БД:

```bash
docker compose stop web timer
docker compose exec -T db pg_dump -U zhanagasyr -d zhanagasyr -Fc > backup.dump
# Сохраните содержимое volume app_data отдельным архивом с тем же идентификатором снимка.
docker compose start web timer
```

Восстанавливайте `pg_restore --no-owner` сначала в отдельную пустую staging-БД, вместе с соответствующим volume приватных файлов. Проверьте полный сценарий и контрольные суммы файлов перед переключением production. Процедура PostgreSQL в этой среде пока не испытана.

## Обновление

1. Просмотрите изменения и миграции; дождитесь завершения текущих экзаменов или согласуйте окно обслуживания.
2. Сделайте и проверьте резервную копию.
3. Остановите web/timer; обновите checkout, соберите новый образ.
4. Выполните `docker compose run --rm setup`, затем `docker compose up -d web timer`.
5. Проверьте health, вход, кабинет, тестовую попытку, private media и timer.

Откат кода не равен откату миграций: при несовместимой схеме восстанавливается согласованная пара кода/БД/файлов. Нельзя удалять историю через `flush` на рабочей среде.
